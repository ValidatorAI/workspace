# Blocker (created / resolved / dismissed)

Type: input-processing skill
Apply when: events `blocker_created`, `blocker_resolved`, or `blocker_dismissed`.

## Procedure

0. Invocation surface: PWR/Knowledge MCP tools may be deferred even when listed — a direct call errors with "Tool does not exist". Recover in one round-trip: `tool_describe` ALL the tool names this event needs (batch them), then invoke via `tool_call` `[{name, arguments}, ...]`. This is routing, not a server outage — do not conclude the MCP is unattached from that error.
1. Read the item: `blockers(item_id: <content_payload.attention_item_id>)` — the attention-item id is the row id, NOT the event id (delivered envelopes sometimes omit `event_id`/`group_id` entirely); confirm status.
   1b. When `content_payload` is `null` (raw-attention-item deliveries carry only category/status/title/project_id/room_id/occurred_at), locate the row by `blockers(project_id)`, or — when the envelope carries no project_id — by `blockers(status: "pending")` unfiltered: system-raised dispatch-failure blockers can have `project_id: null` themselves (room-scoped only), so a project-filtered lookup silently misses the row. Match on `title` (+ `room_id`) and `created_at` == the event's `occurred_at`; never create a new item just because the envelope had no id. The envelope's `occurred_at` is second-truncated while row timestamps carry milliseconds — truncate the row `created_at` to the second before comparing. When NO sibling's truncated `created_at` equals `occurred_at` (event delivery lags row creation by tens of seconds), resolve by clock precedence instead of demanding equality: the event cannot report a row that does not exist yet, so eliminate every row with `created_at` AFTER `occurred_at` and take the closest preceding one — a row created minutes after the event's timestamp is a separate fixture and must NOT be folded into this delivery's dedupe. On a title collision prefer the row with no existing cal-log footprint; when N sibling rows share the title within the same second (a recheck burst's strike 1..N), one delivery maps to the whole cluster — a footprint citing the cluster's item ids and that timestamp satisfies dedupe for every row, so treat the family as one unit, not per-row.
   1c. When the `item_id` lookup returns `Record not found`, the row was deleted (fixture cycling does this). Locate by `blockers(title: ...)` and compare timestamps: a same-title sibling with `created_at` LATER than the event's `occurred_at` is a recreated row, NOT this event's subject — do not act on it (its own lifecycle will raise its own events). Process the event against the vanished row: the only way it held work is an open record citing that id, so the `ai_tasks` id-sweep + cal-log footprint decide created/resolved/dismissed alike.
2. `blocker_created` — the blocker just fired, often raised by PWR itself (e.g. dispatch failure: `meta_text` carries the dispatch error, `source_type: AiTask`/`source_id` names the origin it holds up). Your job is to unstick the origin, never to clear the item:
   - `get_ai_task(source_id)` first. If the origin is already `finished=true`, or `tool_cal_logs(project_id)` shows entries targeting the source entity whose `why_was_it_required` names the blocker_created family, this delivery is already handled (or re-delivered) — verdict do-nothing, no new log.
   - If the origin task is open and stuck on an unusable assignee: call `list_ai_profiles` (config-mcp) BEFORE attempting `update_ai_task(assigneee_profile: ...)` — re-route only when a valid profile actually exists. If no profile exists, or the bad assignee is a deliberate test/probe input, re-routing is not applicable; record that in `actual_task_context`.
   - Never set `resolved`/`dismissed` on a system-raised blocker — leave it pending for human close-out; act on the work it names, not on the item.
3. `blocker_resolved` — the unblock is already applied in PWR. Your job is to unstick the work it held:
   - `ai_tasks(project_id: <item.project_id>, finished=false)` — find tasks whose `description`/`actual_task_context` reference the blocker; append "<blocker id> resolved <date>, can proceed" via `update_ai_task`.
   - If the blocked work belongs to another profile and no task exists, route one: `create_ai_task(description: "Resume <work> — blocker <id> resolved", assigneee_profile: <owner>, input_event_entity_id: <event_id>)`.
   - Update related open `risks`/`dependencies` status items if the blocker was their evidence (`edit` with `item_id`, merge).
4. `blocker_dismissed` — the blocker was cancelled, not cleared. Record why in the referencing tasks ("dismissed <date> by <actor>: <item.meta_text>") so nobody assumes it was fixed.
5. No open work referenced the item: verification log only.

## Tools used

| Tool | Endpoint | Key arguments |
|---|---|---|
| `blockers` (generic) | read-mcp + action-mcp | list = no args beyond filters; get/edit/delete = `item_id`; create = `title` |
| `add_blockers` | action-mcp | required: `title`; optional: `meta_text`, `action_label`, `due_at`, `overdue`, `project_id`/`project_name`, `room_id`/`room_name`, `user_id`/`user_name` |
| `edit_blockers` | action-mcp | required: `item_id`; writable: `title`, `meta_text`, `status`, `action_label`, `due_at`, `overdue` |
| `attention_items` | read-mcp | cross-category list: `category`, `status`, `project_id`, `user_id` |
| `delete_attention_item` | action-mcp | required: `item_id` — only for duplicate/erroneous items you created |
| `tool_cal_logs` | knowledge-mcp | NO `target_entity_id` filter param — list by `project_id` (+ `start_date`/`end_date`, big `per_page`) and match `target_entity_id` in the returned entries; for room-scoped items (`project_id: null`) list by `room_id` instead; for company-scoped items BOTH are null and no filter applies — pull the unfiltered page 1 with big `per_page` and treat that page's oldest..newest `created_at` span as the dedupe window: a blocker_created footprint is always written after the item's `created_at`, so a window whose newest entry post-dates the event delivery and whose grep on the item id + title keyword is zero-hit proves no prior action. The window is valid only when page 1's OLDEST `created_at` is at or before the item's event timestamp — the page is newest-first, so a footprint written between the event and that oldest entry sits BELOW the page-1 cutoff, not on it. When page 1 doesn't reach back far enough, pull page 2..N with `start_date` anchored at the event time and prove each page's oldest `created_at` before declaring zero prior footprint |
| `ai_tasks` / `get_ai_task` / `update_ai_task` / `create_ai_task` | task-mcp | merge into `description`; close the loop |
| `list_ai_profiles` | config-mcp | no args — call before any re-route to an `assigneee_profile` to confirm the target exists |
| `risks` / `dependencies` | read+action-mcp | status items that may cite the blocker |

## Example

```json
{"event_type": "blocker_resolved", "event_id": 42,
 "event_data": {"actor": {"username": "carol"}, "target_type": "AttentionItem",
   "content": "Blocker 'task-mcp not attached to workspace profile' resolved",
   "content_payload": {"attention_item_id": 42, "project_id": 2}}}
```

Run: `blockers(item_id: 42)` → resolved → `ai_tasks(project_id: 2, finished=false)` → task 88 description says "blocked by 42" → `update_ai_task(task_id: 88, description: "<existing text>\n\n[2026-11-02] blocker 42 resolved by carol — unblocked, can proceed")` → `create_tool_cal_log(used_tool_name: "update_ai_task", target_entity_id: "88", change_log: "notified task 88 blocker cleared")`.

## Logging rule

After **each** state-changing tool call, call `create_tool_cal_log` (knowledge-mcp):
`{"used_tool_name": "<tool>", "project_id": ..., "room_id": ..., "topic_id": ..., "target_entity_id": "<entity touched>", "why_was_it_required": "<event_type>", "change_log": "<one line>"}`.

- Unsticking a dispatch-failure blocker: `update_ai_task(task_id, dispatch_attempts: 0)` is the sanctioned re-queue — the tool clears `dispatched/finished/dispatch_error` at zero and the in-process `AiTaskDispatchLoop` (1s poll) re-dispatches. Verify `assigneee_profile` validity by probing the Hermes gateway `GET /p/<profile>/v1/models` (200 = exists; PWR's `AiProfile` table / `list_ai_profiles` can be empty while gateway profiles work fine). A `Net::ReadTimeout` on the dispatch POST does NOT mean undelivered — the agent may still land and start working; check for fresh room messages/cal logs from the task id before assuming retry needed.
- When `tool_search`/`tool_describe` cannot resolve PWR MCP tools at all (empty deferred catalog), the native MCP surface is still reachable as JSON-RPC over HTTP: `POST localhost:3000/task-mcp|knowledge-mcp|action-mcp|read-mcp` with `Authorization: Bearer <MCP_AUTH_TOKEN from repo .env>` and body `{"jsonrpc":"2.0","id":n,"method":"tools/call","params":{"name":...,"arguments":{...}}}`; reads can go via `/api/...` with `OUTPUT_EVENTS_TOKEN`. That is the same tool server, so writes remain compliant (never raw SQL).

## Environment pitfalls

- A test/probe harness that leaks raw `sqlite3.connect(DB).execute(<UPDATE>)` transactions holds the SQLite **WAL write lock** until process exit. Symptom split: ALL MCP `tools/call` fail `SQLite3::BusyException` (the MCP layer writes an audit row per call), while pure-read `GET /api/...` returns instantly. Diagnose the holder: `grep <dev.sqlite3-shm inode> /proc/locks` for a `WRITE` line, map PID to the runner. Procedure: do the read-only triage via `curl -H "Authorization: Bearer <OUTPUT_EVENTS_TOKEN from repo .env>" localhost:3000/api/attention_items/<id>` and `/api/tasks?project_id=..&finished=false` (same rows the MCP tools return), wait for the runner PID to exit, THEN write the cal log via MCP. Never kill the harness; the Hermes MCP client's circuit breaker (5-failure cooldowns) just keeps counting while the lock lasts.
- `/api` list endpoints cap at **per_page=50** even when 100 is requested — prove dedupe-window coverage by the returned id range, not the requested page size. MCP `tool_cal_logs` does honor `per_page=100`, so a 100-entry spillover proves window depth the /api path cannot.
- Probe-shaped items — label-only `meta_text`, `source_id`/`source_type` null, title naming no origin work — always get the verdict verification log only (`used_tool_name: noop-verification`): no room post, no edit_blockers, leave the item pending for human close-out. Once a `noop-verification` log whose `why_was_it_required` is the blocker_created family cites this item's exact `created_at`, it satisfies the blocker_created dedupe for every later re-delivery of it. Never dedupe on a bare `target_entity_id` hit: the id space is shared across attention categories, so noop logs for todos/outcomes items sit adjacent to blocker logs under equal or neighboring numbers — open the matched log entry and confirm the event family before ruling. Fixture cycling: a harness may delete and recreate the same title under successive ids, each id getting its own event of a DIFFERENT family (created → resolved → recreated pending) — a footprint for one sibling never satisfies another; and one family's footprint can pre-date a sibling's row entirely, so verify the cited item id and timestamp, not just the title keyword.

## Guardrails

- Read-before-write: never `add_*` into a category without listing that category for the same scope first — PWR has no dedupe tool.
- Never overwrite existing text with `edit_*`: fetch, merge, write back.
- Attention statuses are exactly `pending` / `resolved` / `dismissed`.
- Event delivery is at-least-once: re-delivery has the same `group_id` / `event_type` / `event_id`. Dedupe via `tool_cal_logs` listed by `project_id`, matching `target_entity_id` in the results (see Tools table — no direct filter param). Before acting a second time: when the envelope carries no `event_id`, match duplicates on (`target_entity_id`, `why_was_it_required` event family, item timestamp) — compare against the ITEM's `resolved_at`/`created_at` as embedded in the existing log's `change_log`, never the log row's own `created_at` (the footprint is always written after the event, so those clocks never line up). A log citing the same item timestamp is the same delivery: verdict do-nothing, no new log written. Still sweep the CURRENT `ai_tasks` snapshot once for late work citing the blocker before finalizing the no-action verdict. A hit on a shared token alone is not a citation: open each matched record and confirm it references the item id or the `source_id` relation — sibling fixtures sharing an assignee/error string match any keyword sweep but are not work this event unblocks, and acting on them is out of scope. Watch numeric ids: `\b<id>` matches INSIDE larger unrelated numbers (external tracker issue "#170" matches a sweep for attention item 70 via `.*70\b` or substring greps) — confirm the match cites the attention item itself.
- When EVERY PWR MCP endpoint (read/action/knowledge/task) answers `SQLite3::BusyException: database is locked`, that is a write-lock held by another process (test harnesses doing direct `sqlite3` DML without commit, or a long transaction), not an unattached server. Orientation can still be done read-only against the WAL db (`sqlite3.connect("file:storage/db/<env>.sqlite3?mode=ro", uri=True)` — readers are never blocked in WAL mode) to fetch the attention row, `tool_cal_logs` footprint and open `ai_tasks`; use it to reach the verdict, but never write through that connection — any state change or `create_tool_cal_log` must still go through MCP once the lock clears. A do-nothing/verification-only verdict is unaffected by the lock (no write is owed), so don't stall waiting for it and don't kill someone else's running process.
- `ai_tasks`/`tool_cal_logs` list responses often exceed the result budget and persist to a spillover file — grep that file with `search_files` (content mode, regex like `blocker[ #:]*<id>\b|<title-keyword>`) instead of re-requesting the API. One probe per assertion; when computing the page's timestamp window and entry count, a single `terminal` python one-liner reading the spillover JSON gets both in one shot. On unattended surfaces (api_server) the approval policy hard-denies scripted parsing outright — `execute_code` is BLOCKED and no approval exists to grant mid-run — so go straight to `search_files` count-mode probes: the row-count probe uses ONLY the structural-marker pattern and the citation probe uses ONLY the keywords, as one combined alternation (`marker|keyword`) returns a merged count that proves neither assertion.
- A zero-hit grep proves nothing until you show the file contained the records you expected: count a structural marker that appears exactly once per record — `"target_entity_id"` in a cal-log spillover, `"assigneee_profile"` in an `ai_tasks` spillover (cross-checking a second marker like `"finished": false` and getting the same count proves the file parses as expected) — and sanity-check the count against the list call's scope — or, on a re-delivery check, against the sweep count recorded in the prior footprint log's `change_log` (matching counts prove the snapshot still covers the same population). Truncation or the wrong spillover file otherwise masquerades as "nothing cites the blocker" and drives a false do-nothing verdict.
- Recheck-strike re-deliveries of a dispatch-failure blocker can leave the origin task permanently unsavable via MCP: the harness pushes `dispatch_attempts` past the model cap (>3), and `update_ai_task` validates the WHOLE persisted row, so even a benign `actual_task_context` append fails with "Dispatch attempts must be less than or equal to 3". When step 2's "record in actual_task_context" is blocked this way, record the verdict in `create_tool_cal_log` (target = the task id) and flag the counter reset as the human close-out need — never write the row via raw SQL.
- A transport-session expiry mid-call to task-mcp `ai_tasks` surfaces as `outcome_uncertain` because the client flags every task-mcp tool as write-capable — but the LIST form (filters only, no `item_id`/mutating fields) has no side effect, so re-issue the identical filter set against read-mcp's `ai_tasks` twin rather than stalling on the unknown outcome or probing state first.
- `tool_cal_logs` ignores `end_date` (ISO with Z suffix returned rows above the bound); build a deep dedupe window by paging `page=1..N` with a wide `start_date` and prove each page's oldest `created_at` before declaring "no prior footprint".
- `blocker_dismissed` with `meta_text: null` and no `target_id`/`source_id`: the item says nothing about what it blocked. Sweep `ai_tasks(project_id, finished=false)` for the item id AND the title keyword (e.g. "HA-30r"); if nothing cites it, verification log only — do not invent unblock work.
